# 0.4 first iteration: book details lookup and read-only sharing

Status: development branch, 2026-11-05. This is not a signed or certified 0.4 package. The published 0.3.0 package is unchanged.

Design records: [explicit lookup](adr-0.4-metadata-lookup.md) and [read-only shelf sharing](adr-0.4-read-only-sharing.md).

## Book details lookup

Book Details has a collapsed **Find book details** section. Opening it makes no network request. An owner explicitly searches Open Library by a valid ISBN or by at least three title characters, optionally adding an author. ISBN lookup resolves the edition directly and verifies that the returned identifiers include the requested ISBN; selecting it reuses the account-scoped cached response. The owner chooses an edition, sees source URL, ISBNs and language evidence, compares supported fields, and stages only checked differences. The existing Save/Discard and metadata-revision check decide whether the staged fields become Library edits. Manual book editing remains usable if Open Library is unavailable. No scan, page load or recipient action calls the provider. Browser requests are cancelled when the user leaves the book. Search and edition responses are account-scoped cached for 15 minutes and are not stored in browser caches.

Supported staged fields in this iteration: title, subtitle, publisher, publication year/date, description, subjects and individually selected validated ISBNs. The editor still stores accepted values as manual corrections. Provider provenance, conditional reversal, language assignment, broader identifier reconciliation, Google Books, cross-provider ranking and selected-book batch work remain open under [#179](https://github.com/utrost/Library/issues/179). The UI must not imply that staging alone saves a book. Google Books remains behind the planned provider interface because its [public-data API requests require an API key](https://developers.google.com/books/docs/v1/using). Open Library's [ISBN API](https://openlibrary.org/dev/docs/api/books) resolves the requested edition; its [Search API](https://openlibrary.org/dev/docs/api/search) currently exposes only a selected edition per work, so title search cannot enumerate every edition of a work. Its [API guidelines](https://openlibrary.org/developers/api) rule out bulk use and call for cache/rate discipline. A database-backed slot spaces external request starts by at least one second across Library workers; when busy beyond 2.5 seconds it returns a retryable 429.

An administrator can disable Open Library lookup by setting the Library app value `openlibrary_lookup_enabled` to `no`; direct editing remains available. An in-app provider setting is still to be designed.

## Read-only sharing

**Shared libraries** is a separate surface linked from Library navigation and settings. The owner first shares the shelf folder read-only in Nextcloud Files; the recipient accepts that share. The owner then selects an enabled Library shelf and one local user from a three-letter typeahead, sees the chosen account ID, reviews the recipient and existing Files access, and confirms. Recipient discovery and confirmation use Nextcloud's collaborator-search visibility policy, including its filter event on NC33/34. The review warns that Files access can expose every file and subfolder in the shelf, including files Library has not indexed. Confirmation rechecks the folder identity and read-only Files access. Library does not create a Files share. It records the owner, recipient, root ID and underlying folder file ID. A recipient sees only active grants for a root whose current folder still has that file ID and is still readable to them. Each book, cover and Open link repeats the recipient's file-identity and read-permission check. Publication title, canonical author display where available, subtitle, publisher, date, language, subjects and description can be shared; paths, ratings, reading state, favorites, lists, notes, comments, diagnostics and owner-only action URLs are omitted. The source catalogue stays in the owner's account and is never copied or indexed for the recipient.

The owner can revoke a Library grant. The owner list shows each recipient's display name and exact account ID, including in the Remove access label. Revocation leaves existing Files shares intact; those must be removed separately in Nextcloud Files if the owner wants to end file access too. For managed Files shares created by an earlier development build, Library attempts exact-share cleanup and leaves a retryable hidden row on failure. Shelf path changes, disabling or deletion revoke grants before changing the shelf; failed legacy Files cleanup leaves a shelf mutation unchanged. Moving a source folder or changing Files permissions makes the recipient view fail closed. Covers use a validated owner override where available, otherwise the recipient-readable file's Nextcloud preview or a generic placeholder, with private/no-store responses. Open hands off to Nextcloud's file-ID URL; the recipient's Files permission remains authoritative.

The first UI pages are deliberately simple and read-only. Shared book listings use ID cursors and a bounded 80-book page; title/author search requires three characters. Search uses the owner's curated author assignment when ready and source creator text otherwise. Returning from a shared book keeps the search and page cursor. Owner grant lists are currently capped at 100 rows. Cover, search, grant lifecycle and multi-user behavior need the privacy, performance and database matrix in [#180](https://github.com/utrost/Library/issues/180) before release. Sharing cannot override writable access that a recipient already has through another Files mount; the owner must adjust that Files permission separately. The first iteration does not offer shared personal overlays, groups, public links, shared annotations or admin roots.

New grants are a single Library database write after existing Files access has been checked. A repeated confirmation is successful only while the existing grant is ready and its folder identity and Files mode still match the review; changed access tells the owner to remove the stale grant and share again. Grant/revoke and shelf changes use Nextcloud locks. The earlier managed-share recovery path remains only for development builds that created Files shares. The recipient interface needs measured search and paging behavior on a large shared shelf before it can be considered production-ready.

An uninstall repair step attempts to revoke all Library grants on disable and uninstall. A persistent shutdown marker blocks new grants during cleanup; enabling the app clears that marker. NC34 disposable testing found that Nextcloud disables the app even if a repair step fails, leaving an earlier managed Files share active. This is why new grants require existing Files access. The hook remains best-effort recovery for earlier development shares; an unresolved Files share must be removed in Nextcloud Files. Existing manual Files shares intentionally remain after Library is disabled.

Shared-shelf search now matches the displayed canonical author names when author links are ready, and falls back to imported creator text while those links are pending or absent. A disposable two-user lifecycle fixture verifies this behavior and the reuse-only Files boundary on NC33.0.9, NC34.0.4 and NC35.0.0 with SQLite. It covers grant rejection without Files access, grant/revoke with an accepted read-only Files share, disable/re-enable, app removal and preservation of independent Files shares.

Read-only SQL timing on a populated NC34 MariaDB catalogue of about 108,000 books used the largest existing shelf (about 5,000 books) and a full-owner upper bound. Warm shared-search queries on the shelf took roughly 38–48 ms for common/no-match terms; the full-owner upper bound took roughly 47–57 ms. The prior source-credit-only query took roughly 16–21 ms in the same warm runs. One cold shelf query took 121 ms with the new query and 650 ms with the prior query; cache state makes those cold values unsuitable for a comparative speed claim. These figures measure SQL only, not browser response time, Files permission checks or cover loading. The canonical query costs more CPU, but this sample does not indicate a two-second SQL bottleneck. Full shared-view load and larger-shelf measurements, plus PostgreSQL coverage, remain under [#191](https://github.com/utrost/Library/issues/191).

### Manual sharing checks for this draft

Use disposable owner and recipient accounts. Search for a recipient with fewer than three characters, then with three; choose a suggestion by mouse and keyboard, change the shelf and confirm the choice clears, and check that an undiscoverable user cannot be submitted by editing the hidden form field. Review without a Files share and confirm Library asks for one. Share the folder read-only in Files, accept it, then review and confirm a Library grant. Open a shared book and its cover; then remove Files access or replace the source folder and confirm both fail closed. Revoke the Library grant and verify that the owner's pre-existing Files share remains. Disable Library and confirm the app grant is gone while manually granted Files access remains. Complete these checks on NC33–35 before release.

## Release gate

Before enabling this on a real library, complete the linked issue acceptance: NC33–35 and SQLite/MariaDB/PostgreSQL migration checks; multi-user grant/revoke, identity-change and existing-share cases; preview and search response-time checks on a large catalogue; accessibility review; provider throttling, privacy/terms review and provenance; signed-package certification and handbook update. This document describes code intent, not evidence that those checks passed.

Automatic draft-PR CI has run source checks, static gates and a disposable Nextcloud smoke on prior commits; the current commit must pass CI again. A focused SQLite two-user sharing lifecycle and canonical-author search matrix passed on NC33–35.
