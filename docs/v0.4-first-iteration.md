# 0.4 first iteration: book details lookup and read-only sharing

Status: development branch, 2026-11-05. This is not a signed or certified 0.4 package. The published 0.3.0 package is unchanged.

Design records: [explicit lookup](adr-0.4-metadata-lookup.md) and [read-only shelf sharing](adr-0.4-read-only-sharing.md).

## Book details lookup

Book Details has a collapsed **Find book details** section. Opening it makes no network request. An owner explicitly searches Open Library by a valid ISBN or by at least three title characters, optionally adding an author. ISBN results are limited to editions whose returned ISBN matches. The owner chooses one edition, sees source URL, ISBNs and language evidence, compares supported fields, and stages only checked differences. The existing Save/Discard and metadata-revision check decide whether the staged fields become Library edits. Manual book editing remains usable if Open Library is unavailable. No scan, page load or recipient action calls the provider. Search and edition responses are account-scoped cached for 15 minutes and are not stored in browser caches.

Supported staged fields in this iteration: title, subtitle, publisher, publication year/date, description, subjects and individually selected validated ISBNs. The editor still stores accepted values as manual corrections. Provider provenance, conditional reversal, language assignment, broader identifier reconciliation, Google Books, cross-provider ranking and selected-book batch work remain open under [#179](https://github.com/utrost/Library/issues/179). The UI must not imply that staging alone saves a book. Google Books remains behind the planned provider interface because its [public-data API requests require an API key](https://developers.google.com/books/docs/v1/using). Open Library's [Search API](https://openlibrary.org/dev/docs/api/search) supplies edition-level results; its [API guidelines](https://openlibrary.org/developers/api) rule out bulk use and call for cache/rate discipline. A database-backed slot spaces external request starts by at least one second across Library workers; when busy beyond 2.5 seconds it returns a retryable 429.

An administrator can disable Open Library lookup by setting the Library app value `openlibrary_lookup_enabled` to `no`; direct editing remains available. An in-app provider setting is still to be designed.

## Read-only sharing

**Shared libraries** is a separate surface linked from Library navigation and settings. An owner selects one enabled shelf and one existing local user, reviews the recipient and whether Files access will be created or reused, then confirms. The review explicitly warns that a Files folder share exposes every file and subfolder in the shelf, including files Library has not indexed. Confirmation rechecks the folder identity and Files-access mode. Library creates a Nextcloud Files user share with read permission only when the recipient has no existing readable mount. It records the owner, recipient, root ID, underlying folder file ID and managed Files share ID. A recipient sees only active grants for a root whose current folder still has that file ID and is still readable to them. Each book, cover and Open link repeats the recipient's file-identity and read-permission check. Publication title, author, subtitle, publisher, date, language, subjects and description can be shared; paths, ratings, reading state, favorites, lists, notes, comments, diagnostics and owner-only action URLs are omitted. The source catalogue stays in the owner's account and is never copied or indexed for the recipient.

The owner can revoke a grant. Library hides the catalogue grant first, then removes only a Files share it created. If Files cleanup fails, the grant stays hidden and a retryable cleanup row remains. Shelf path changes, disabling or deletion revoke grants before changing the shelf; a failed Files cleanup leaves the shelf unchanged. Existing Files shares are not deleted by Library. Moving a source folder or changing Files permissions makes the recipient view fail closed. Covers use a validated owner override where available, otherwise the recipient-readable file's Nextcloud preview or a generic placeholder, with private/no-store responses. Open hands off to Nextcloud's file-ID URL; the recipient's Files permission remains authoritative.

The first UI pages are deliberately simple and read-only. Shared book listings use ID cursors and a bounded 80-book page; title/author search requires three characters. Returning from a shared book keeps the search and page cursor. Owner grant lists are currently capped at 100 rows. Cover, search, grant lifecycle and multi-user behavior need the privacy, performance and database matrix in [#180](https://github.com/utrost/Library/issues/180) before release. Sharing cannot override writable access that a recipient already has through another Files mount; the owner must adjust that Files permission separately. The first iteration does not offer shared personal overlays, groups, public links, shared annotations or admin roots.

The Files share and Library grant are separate writes. A new grant now reserves a hidden Library row before Files share creation and marks the Files share with a random recovery token. A failed or interrupted create remains owner-visible as cleanup pending; Remove access retries exact-share cleanup. Grant/revoke and shelf changes use Nextcloud locks. Failure injection, edited share notes and app-disable/uninstall recovery remain release blockers under [#197](https://github.com/utrost/Library/issues/197). The recipient interface also needs measured search and paging behavior on a large shared shelf before it can be considered production-ready.

Disabling or uninstalling Library currently leaves any Nextcloud Files share in place. Owners must revoke access before disabling the app, or remove the Files share manually afterward. The release-gate lifecycle work must address this explicitly.

## Release gate

Before enabling this on a real library, complete the linked issue acceptance: NC33–35 and SQLite/MariaDB/PostgreSQL migration checks; multi-user grant/revoke, identity-change and existing-share cases; preview and search response-time checks on a large catalogue; accessibility review; provider throttling, privacy/terms review and provenance; signed-package certification and handbook update. This document describes code intent, not evidence that those checks passed.

Source preparation completed for this branch: frontend asset build (807,696-byte runtime bundle), generated English/German/Arabic locale bundles, PHP and XML syntax checks, and `git diff --check`. Runtime, browser, database migration, provider integration and multi-user acceptance checks have not been run for this iteration.
