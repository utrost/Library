# Personal book lists and notes

Status: accepted as sufficient for the current feature slice; `0.2.0-alpha.12` on `develop/0.2` adds performance improvements and regression coverage. Private lists, descriptions, per-entry notes, batch membership, pagination and manual ordering are implemented. Export/import, shared lists and discussion threads remain future scope. See the [current verification report](compatibility-evidence/2026-09-26-alpha12/README.md).

Alpha.12 batches list counts and membership queries, prefetches a page's book metadata, coalesces simultaneous client reads and saves notes without a full-page reload. Live file access checks and list revision checks remain enforced. Benchmarks use 150 lists and 6,000 entries; these are service timings on disposable SQLite instances, not promises for every installation.

[First implementation test evidence](compatibility-evidence/2026-09-25-lists-alpha1/assessment.md): backend integration and Chromium/Firefox/mobile Lists checks pass on Nextcloud 33.0.9, 34.0.4 and 35.0.0 with the 40 English Gutenberg books.

Developer UX revision (`0.2.0-alpha.3`): saved list shortcuts and Create a new list are available under Lists in navigation. Selection uses one compact toolbar; More actions reveals one operation at a time. The separate batch panel and catalogue creation form are removed.

Previous revision (`0.2.0-alpha.2`): an inline existing-list selector and Add to list button sit above the books; there is no popup or batch-menu step. A separate Create a new list action opens a small inline name form. The target list is preselected when arriving from Lists. Saved filter shortcuts appear directly below Collections, before Lists. New versioned asset URLs invalidate the earlier cached layout. Follow-up validation uses the focused developer smoke; the full compatibility suite is deferred until UX acceptance.

## User outcome

A user can create a list such as Summer reading, Learn linear algebra or Sources for my article, explicitly add books, arrange them, and record why each book belongs there. The same book can belong to several lists with different notes in each.

## Existing collections and the new feature

The current `SavedCollectionService` stores named catalogue filter combinations in `library_saved_collections`. Their results change as books and metadata change. They do not store explicit book membership, ordering or list-specific notes.

Keep this behavior available as saved searches/smart collections. Manual lists have explicit membership: a metadata edit or inference run must not silently add or remove books. The eventual navigation should make the difference clear, without changing existing saved filter semantics.

## First useful scope

- Create, rename and delete a personal list with a title and editable description/general note.
- Add one book from its catalogue/sidebar/detail actions or add explicitly selected books in a batch. The picker shows existing lists and Create list, with clear Already in this list feedback.
- Add the same book to several lists, but prevent duplicate membership within one list.
- Remove books from a list without deleting source files or removing catalogue items. Deleting a list removes its membership and notes only, with clear confirmation and recovery expectations.
- Set a manual reading order. Provide Move up/down or Move to position controls as well as drag-and-drop so ordering works on keyboard and mobile.
- Add and edit a private note on each list entry, for example Read chapters 2–4 or Compare this approach with the previous book. This note belongs to that book in this particular list.
- Browse a paginated list with its notes, open books using the existing handoff, and locate lists containing a book from its details.

Use an editable list description and one editable note per entry for the initial interpretation of comments. Timestamped discussion threads, replies and shared collaboration are possible later features; confirm that interpretation during UX review.

## UX example

```text
Learn linear algebra
Description: A reading sequence for this autumn.

1. Book A   “Start with chapters 1–3.”
2. Book B   “More exercises; compare chapter 2 with Book A.”
3. Book C   “Advanced material for later.”

Add books · Edit list · Reorder
```

Keep saved manual order separate from temporary title/author sorting. Filtering a list hides entries without removing them; do not let reordering a filtered subset silently rearrange hidden entries. Show Added to list / Already present / Could not add outcomes for batch actions and preserve selection after failures.

## Data and privacy boundaries

Lists and notes are app-owned personal data. They are separate from Nextcloud file comments, which have file-level visibility, and from bibliographic metadata. Never publish list notes as file comments, OPF fields or shared sidecars implicitly.

Introduce user-owned lists plus membership rows linking a list to a catalogue item, with order, note and timestamps. Enforce ownership and current file access on reads and mutations, a unique list/item membership and revision checks for concurrent note/order edits. Reuse existing safe text rendering and length limits; raw HTML is not an initial note format.

Ordinary rescans, metadata edits and same-identity renames must preserve membership and notes. Keep inaccessible or missing publications as neutral Unavailable entries without exposing inaccessible titles, paths or file details. Preserve the user's own entry note and order, so a temporarily missing book does not erase their planning work.

Explicit root removal or forgetting a catalogue item retains an unavailable entry with its unresolved item/file IDs and personal note. These references deliberately do not cascade-delete the entry. The stored Nextcloud file ID guards against a catalogue ID being rebound to a different file. Users can remove the entry; explicit relinking is future scope. Never automatically attach it to a different book merely because a filename matches. Restore visibility only after access and identity are revalidated.

Lists and their notes must eventually be covered by documented export/import and backup semantics. A bibliographic metadata export alone does not constitute a backup of these personal lists. Define this before promoting the feature as portable; database backups remain the recovery baseline until list export exists.

## Dependencies and sequencing

This feature can be developed independently of inference, OPF writing and physical filing. It needs list/membership persistence, ownership checks, note editing, ordering, batch add/remove and list navigation. Ordinary list edits do not require a scan job.

Inference may improve the metadata displayed in a list but cannot change its membership. Future filing must preserve list references when catalogue identity is preserved, or explicitly reconcile them if a supported move changes identity. Existing file handoff and permission checks can be reused.

Suggested delivery order:

1. Prototype list creation and Add to list alongside existing saved collections; validate naming/navigation.
2. Implement personal lists, explicit membership, descriptions and per-entry notes.
3. Add accessible manual ordering, batch actions and clear unavailable-entry behavior.
4. Add portable list export/import; consider shared lists and comment threads after the personal workflow is proven.

## Acceptance criteria

- A user can create a list, add selected books, order them, write notes and return later to the same state.
- Two lists can contain the same book with independent notes; adding it twice to one list is harmless.
- Rescans and metadata edits preserve membership, order and notes.
- Removing a list/member never deletes a book or modifies its bibliographic metadata.
- Other users cannot read lists/notes; inaccessible source-file details are withheld.
- Concurrent editing, failed batches and unavailable books have visible outcomes without silently dropping user work.
- Existing saved collections continue to resolve their saved filters.

List editing correction (`0.2.0-alpha.4`): changing the name/description no longer disables entry movement or removal. Entry refreshes retain the unsaved list draft.

## Development loop

Default workflow agreed with the user (2026-09-25): deploy small working slices to the existing developer instance at `http://100.123.149.120:8088` (`nextcloud`, NC34.0.3), run a short feature smoke check, and obtain user UX feedback there. Do not run the full test suite or create compatibility instances for every edit. Back up app/database before a schema-changing deployment. After deployment, gracefully reload Apache workers to invalidate PHP’s 60-second opcode cache, and verify the rendered asset version before testing. Never run disposable-fixture tests against the developer's existing books.

For Lists, `node scripts/smoke-personal-lists.mjs` checks browser startup, temporary list creation/edit/deletion and catalogue startup. It removes only its own temporary list and app password. It does not rescan, modify publication metadata or replace the developer's fixtures.

After the feature works as expected and UX is accepted, run deeper integration, all Playwright scripts and fresh-install/upgrade compatibility checks on disposable NC33–35 instances. Targeted regression checks can run sooner for changes to permissions, data integrity or migrations. Fresh instances are a milestone/release gate, not the default edit cycle.

The disposable helper remains available when isolation is needed. `start` reuses an existing instance, `deploy` copies the current build and runs upgrades, and `test` runs the backend integration and Chromium/Firefox/mobile Lists scenarios. Tests remove the lists they create. The 40 English Gutenberg books stay indexed between runs.

```sh
# First setup; provide the existing English Gutenberg fixture archive.
LIBRARY_BOOK_FIXTURE_ARCHIVE=/path/to/gutenberg-en-40.tar.gz bash scripts/dev-lists-instance.sh start

# When working in isolation, reuse the instance after edits.
npm run build
bash scripts/dev-lists-instance.sh deploy
bash scripts/dev-lists-instance.sh test

# Explicit teardown when finished.
bash scripts/dev-lists-instance.sh stop
```

The default environment file is `/tmp/library-lists-dev/34.0.4.env`. Reports are kept under `/tmp/library-lists-dev/reports/34.0.4`. Set `NC_VERSION=33.0.9` or `NC_VERSION=35.0.0` for milestone compatibility checks. Use `LIBRARY_BETA_ARCHIVE` during initial setup to rehearse a beta-to-alpha upgrade. The helper only deploys to/removes containers carrying its own disposable label; ports bind to loopback. These SQLite fixtures are development environments, not production deployments.

Fresh installation and upgrade checks belong at feature/release milestones. Everyday code changes reuse the running development instance. List filtering, temporary sorting and portable export/import are not in this first implementation. Database backup of both `library_lists` and `library_list_entries` is required to recover personal lists and notes.
