# Library 0.4 — work through your incoming books

Updated 2026-11-09 for **0.4.0-alpha.7**. Use this handbook while processing your real collection in your normal Nextcloud account. Keep the corrections, lists and decisions you make. Testing consists of checking that each everyday action has the expected result and recording the exceptions.

Confirm the installed version at the start of a session. This handbook describes the alpha.7 workflow; it is not a record of completed tests. See [current implementation and remaining acceptance](0.4-implementation-status.md). The [technical test handbook](human-test-handbook.md) covers separate regression, recovery and failure-injection exercises.

## The workflow at a glance

**Incoming directory → visible in Nextcloud Files → Library shelf → scan → Review and organise → correct/enrich/organise → Done → browse and read.**

You can expose and index the full incoming collection of approximately 6,000 books. Then curate it in manageable groups, using the same account that will own the finished catalogue. There is no requirement to create a second catalogue, copy all books into a test account, or migrate your corrections afterwards.

Three concepts matter:

| Concept | What it means |
| --- | --- |
| Physical incoming directory | The actual files and their companion files. It must be accessible through Nextcloud Files before Library can use it. |
| Incoming shelf | A Library root pointing to that Files folder. The name **Incoming** is your label; it does not trigger a special file-moving rule. |
| Incoming review queue | Persistent review decisions in **Review and organise**, grouped by shelf and first-indexed UTC date. It tracks what you have reviewed. |

**Done means reviewed.** It does not move a file, remove it from ordinary browsing, mark it as read, or write corrected metadata into the EPUB. Physical filing into a different folder is a separate decision; automatic filing after review is not implemented.

## 1. Connect the real incoming directory once

### Prepare the recovery baseline

Before indexing and curation, confirm you have a recoverable backup of the incoming files and a current Nextcloud database/configuration/appdata backup. The files protect original book contents; the database/appdata protect Library corrections, lists and decisions. Keep the backup outside the incoming shelf.

Record the installed version, existing catalogue count and the approximate incoming file count/size privately. Keep original filenames, nested folders, OPFs and cover files together. There is no need to hash every book before ordinary curation; keep a source-byte baseline for any book you intend to overwrite or delete.

### Make the directory appear in your Files account

If the books already live on the server, an administrator can expose that directory using Nextcloud's Local external-storage backend. Restrict availability explicitly to your account or the intended group. A container deployment also needs the path visible to the app and cron/worker runtimes. Use the deployment's existing storage conventions; do not guess host/container paths or recursively change permissions on the collection.

If mapping is unsuitable, upload or synchronize the directory through Nextcloud Files/WebDAV into its intended long-term location. Avoid exposing both an original and an uploaded copy as Library roots.

**Before opening Library:**

- [ ] The incoming folder appears under your account in Nextcloud Files.
- [ ] Its subfolders and a few EPUB/PDF files are visible and can be opened/downloaded.
- [ ] OPF and other companion files remain alongside their books.
- [ ] Access is limited to the intended people.

A read-only source mount is suitable for catalogue curation: Library corrections are stored in Library. It will prevent physical deletion and source write-back. A writable mount can also be used; ordinary Save, path extraction, provider acceptance and organization do not write publication bytes.

Library cannot index an arbitrary host path. Files copied directly on the server may first need a Nextcloud file-cache refresh scoped to this directory/account. That administrator step makes files visible to Nextcloud; it does not replace the Library scan. For Local storage background, see the [Nextcloud documentation](https://docs.nextcloud.com/server/stable/admin_manual/configuration_files/external_storage/local.html), using the version matching the installation.

### Add and scan the shelf

1. Open **Library settings** and add the folder using the path visible in Files.
2. Give the shelf a clear name, for example **Incoming**.
3. Avoid overlapping roots: if an existing Library root already includes this directory, use that scope rather than index the parent and child separately.
4. Choose **Scan this shelf**. Leave cron running so the job can execute.
5. Watch scan history for completion, failures and metadata errors. You may browse already indexed books while indexing continues.
6. Compare the results with the source directory. Investigate unexplained omissions rather than expecting one catalogue row per filesystem file: covers, companion OPFs and unsupported files affect the count. RAR archives and loose EPUB component folders are not standalone EPUB/PDF books; they need a separate, deliberate preparation step before indexing. Do not unpack archives into the live shelf blindly.

The scan can cover all 6,000 books. You do not have to review them all at once. Scan duration is background processing; record it separately from the responsiveness of Search, Sort or Save.

**Check while working:** are the right files appearing, can you open them, are titles/authors plausible, and are missing metadata/errors explained? Record a few representative exceptions. Do not restart a full scan simply because the queue still says Running.

## 2. Your first working session

Choose 10–20 real books you actually want to clean up, ideally one natural subfolder or a few related titles. This is a working selection from the full catalogue, not a separate test dataset.

1. Open **Review and organise** and choose the incoming **Shelf**. Optionally narrow it to an indexing day; leave the date empty to work across the whole shelf.
2. Inspect several books before deciding what needs changing. Good metadata can be accepted without enrichment.
3. Use path extraction where filenames contain better information; use provider lookup where bibliographic details are missing.
4. Correct author/series/genre assignments and other fields that matter to you.
5. Save or apply the intended changes, then check one or two books again from ordinary browsing.
6. Mark the reviewed books **Done**. Defer uncertain books rather than guess.
7. Leave the page and reopen it. Continue from the queue.

The first session should finish with useful corrected books and a short list of genuine problems. It does not need to exercise every feature.

## 3. Use the incoming queue as your worklist

Incoming batches use **first-indexed UTC date and shelf**. A large scan crossing midnight may create more than one date group; multiple scans on one day can appear together. Re-scanning an unchanged book does not create a new intake batch.

| Situation | Action | Check the result |
| --- | --- | --- |
| Details already look good | Mark Done after review | The decision survives a reload; the book remains available in the ordinary catalogue. |
| You can fix it now | Open Details, correct it, save, then return | Saved changes and the batch/filter/cursor are retained when you go Back. |
| You need to research an edition or author | Defer for one day | The defer decision persists; return after its deferral period. |
| Several books need the same correction | Select the exact books and prepare an organization job | Preview contains only that selection and the intended old/new values. |
| The current filtered page looks empty | Use **Continue to older books** when offered | The queue automatically skips empty 50-record windows, checking at most 200 records per interaction. It distinguishes reaching the end from reaching that work limit. |
| A reviewed book reappears | Inspect its latest change/history | Decisions are revision-bound; a later metadata revision can require review again. |

After a no-change rescan, previously unchanged Done/deferred decisions should remain. Removing and reimporting a catalogue file can create new incoming membership; do not use removal/reimport as a routine queue reset.

Complete the edits first, then mark Done. Otherwise your own later correction may legitimately bring the book back into review. The queue supports resumable curation; it is not a physical quarantine folder and does not hide all unfinished books from normal browsing.

## 4. Choose the right correction tool

### A. The filename or folder contains the answer

Choose **Extract metadata from this shelf** in Incoming books, or open **Extract metadata from paths** from navigation. The shelf shortcut scopes the parser to the shelf, not just the checked books. Narrow the folder and review selected rows before applying. **Back to incoming books** restores the queue context.

- Limit the folder/selection to the group you are working on.
- Select or configure the pattern; keep useful patterns for reuse.
- Assign different patterns per file when the folder contains mixed naming conventions.
- Inspect each proposed field. Pay particular attention to underscores, subtitle separators, author order, ISBN, publisher and year.
- Use per-row Apply when working individually; apply a reviewed batch only where the assignments and selected fields are right.

**Check:** only approved fields/books change, the filename remains unchanged, and the parser reports nonmatches instead of inventing values. If a pattern needs adjustment, record the pattern and a sanitized filename example. Finish by returning to incoming review and marking the completed work Done.

### B. You need external bibliographic details

Use **Find book details** for one book or a selected group. From Incoming books, check the rows and use that action. **Back to incoming books** restores the shelf, filter, page and checked rows. Reloading the lookup view retains its incoming return context.

Start with 5–10 genuinely incomplete books, using **Fill missing fields**. Inspect title, author, language, format and edition even when an ISBN matches. Select only the fields you trust. Try **Other editions** when the first result is the wrong edition. An unmatched book can remain unresolved; do not replace plausible metadata with a guess.

Bulk lookup accepts at most **50 books per run**. Choose useful groups as you work; do not automatically send all 6,000 books to providers. Open Library needs no key; Google Books requires the configured administrative setup. The alpha.8 DNB and Library of Congress adapters also need no key; select them only on alpha.8 or later. Live LoC acceptance is pending endpoint availability. Queries go to the chosen provider, so leave sensitive material out of online lookup. Google Books cover saving remains unsupported; Open Library cover comparison requires an explicit choice where offered.

**Check:** query/edition choices survive leaving and reopening the run, changes apply only to approved fields, conflicts remain visible, and successful rows do not disappear into an unexplained redirect. A failure on one book must not be represented as failure of every successful row.

### C. Several books need the same organization

Select the books from Incoming books, the catalogue, a personal list or a collection and use **Organise selected books**.

Useful real tasks include assigning one publisher, correcting a language, adding a genre, setting a series or replacing a wrongly parsed author. Start with one small useful group. Read the before/after preview and skip exceptions. Empty replacement values mean clearing a field; confirm that this is intended.

**Check:** author order and add/remove/replace semantics are correct, only selected IDs are affected, and job progress/outcomes remain visible after a reload. Pause/resume when you actually need a break. Cancellation stops remaining work; it does not undo already applied books. Conditional Undo may refuse later edits or changed source files, so do not treat it as an unlimited backup.

The technical limit is **5,000 books per job**, not a recommended work-session size. There is no benefit in combining unrelated corrections into one large job.

### D. Individual details need judgment

Use the normal editor for a book's title, authors, series, genres, subjects, classifications, languages and description. Keep custom genres where useful; use a parent/child hierarchy only where it improves your browsing. Preserve uncertain imported classification strings rather than assigning a scheme by guesswork.

**Check:** names are selectable after the minimum search length, Save commits the intended changes, Discard preserves the previous saved values, and the action bar remains reachable. Notice layout, unclear terminology and missing feedback as part of everyday use. You do not need to introduce deliberately wrong metadata to test the editor.

## 5. Use the cleaned books normally

The incoming shelf is part of your catalogue immediately. You can read and organize books before the entire intake is finished.

| Real task | What to watch for |
| --- | --- |
| Find a corrected book by title/author/genre | Accepted values appear in search and entity pages; Back keeps the originating view. |
| Sort, filter and page through the larger catalogue | Results are correct, visible progress appears promptly, and rapid changes do not restore stale results. Aim for usable interactive responses under two seconds under measured conditions. |
| Add useful books to a reading list | Membership and ordering persist; lists can support your next working session. |
| Set To read, Reading or Finished when appropriate | Status is retained and usable in filtering/sorting; review Done and reading Finished remain distinct. |
| Open a book on desktop/tablet or through Files | The intended source opens. Alpha.7 does not promise synchronized reader position; Recently opened is not actual reading progress. |
| Create/link a reading note | The correct document opens; unlinking a note leaves the document intact. |
| Use Nextcloud search or Smart Picker | Accessible owned-book results work; copying a reference does not grant another person access. |
| Adjust Home and the native Dashboard widget | Your chosen list/recent activity is useful; health counts show when their snapshot is pending or dated. |

If you normally switch devices, do so during your actual work. Record clipped controls, lost context, confusing empty states or slow interactions when they occur. Testing on mobile does not require repeating all 6,000 records.

### Share only when it is a real intended action

For an intended recipient, choose either a Files-backed shelf grant or **Selected books only — no Files share**. Review the disclosed access before confirming.

Selected-book grants are a fixed snapshot of 1–100 books from one shelf. Adding another book to the source list does not automatically extend an existing grant. Library revocation and removal of a separate Files share are different actions. Recipients must not receive your private notes, ratings or history. Use a disposable fixture for adversarial permission tests; ordinary collaboration can be checked with a trusted intended recipient and authorized books.

## 6. End a session without losing your place

- [ ] Save or Discard open editor drafts; inspect the outcome of any Apply operation.
- [ ] Mark reviewed books Done **after** their corrections. Defer unresolved items.
- [ ] Pause any job you do not want to continue. Closing the browser does not necessarily stop server work.
- [ ] Bookmark the current queue URL if you want to resume that exact shelf/filter/page/selection later. Reload and the provided Back links preserve it; opening a fresh navigation link starts its default view. Review decisions are saved on the server independently of the URL.
- [ ] Note any unresolved question and the job you plan to resume.
- [ ] Leave and reopen Review and organise once; confirm the saved work and queue context are usable.
- [ ] Record issues while the steps and visible message are fresh.

Let the same working rhythm continue over the collection. You can increase batch size as confidence grows, without changing accounts, reimporting the books or discarding corrections. New arrivals can be added to the same incoming location; make them visible in Files and scan the shelf. Decide later whether scheduled scans suit your routine, using [automatic scans](automatic-scans.md).

### Protect accumulated curation

Keep normal instance and Files backups current. At useful milestones, use **Curation archives** and download the result privately. Let author/series indexing finish before export and pause editing during it: exports collect records over time rather than taking one transactional snapshot.

The archive includes supported corrected metadata, identities, lists, profiles, preferences and other documented curation. It excludes publication/note file contents, sharing grants, credentials, active jobs, original operation-specific Undo journals and **incoming review decisions**. Downloaded archives complement the backup; they cannot restore your full working state alone. Archive jobs normally remain available for seven days.

Do not practise archive restoration over the working account just to tick a test box. Prove recovery on a separate destination with copied files when needed; exact-path/size matching and destination scanning are prerequisites. See [archive scope and restore behavior](curation-alpha6.md#portable-curation-archives).

## 7. Source-file changes are deliberate decisions

Everyday scanning, metadata Save, path parsing, provider acceptance and organization change Library data. They leave book bytes alone. You can finish the intake without writing those corrections into the source files or moving them.

### EPUB write-back

Use **Write metadata to file** only when you actually want the reviewed metadata embedded in an eligible EPUB. First practise one round trip on an independent copy; then use it on real books only with recoverable originals and an explicit field review. Do not use hard links for that practice copy.

Alpha.7 supports eligible EPUB 2/3 on writable local filesystem storage, up to 128 MiB and within its structural limits. Remote/encrypted storage is unsupported. Private ratings, reading state, notes, covers, series, genre hierarchy and classifications are not written. Retained successful originals normally expire after seven days; download anything you need for independent recovery. Verify the current operation completed before interpreting a previous “Original restored” message as success.

### Deletion or “To delete”

If a book is genuinely unwanted, review the deletion preview and confirm only when you want its source removed. Shared OPF and nonempty/protected folder rules still apply. On read-only storage, **Mark for deletion** can hide it while preserving the source; that mark does not schedule later physical deletion and can be undone.

Use expendable copies to test failure handling, shared-sidecar edge cases or recovery from deletion. Do not manufacture those failures in the working collection. Renaming or moving completed files can wait until after curation; **Done does not perform physical filing**. If you later choose another long-term location, make a separate backed-up move/reconciliation plan rather than deleting and rebuilding the catalogue to reset it.

## 8. Record problems with minimal overhead

Keep the working log privately outside the repository. Write one short entry when something fails, surprises you or feels unnecessarily difficult:

```text
Version/date:
What I was trying to achieve:
Shelf/batch/book reference (private):
Actions taken:
Expected / observed / exact visible message:
Did saving finish? Were any unintended books or file bytes changed?
Timing if slow (feedback delay / usable-result delay):
Can I continue? Workaround or recovery used:
Screenshot reference (private):
```

For a slow operation, repeat it a few times if convenient and distinguish first access from repeated access and concurrent background work. For a bulk problem, record the selected count, skipped count, succeeded/conflicted count and job reference. Do not keep pressing Apply when its outcome is unclear; reopen the saved job/history first.

Record successful milestones too: initial scan complete, first working group reviewed, progress retained overnight, a useful provider batch applied and corrections still present after a rescan. This demonstrates real behavior without a result row for every book.

Before publishing an issue or screenshot, replace private book names, paths, users, server addresses and browser chrome with safe examples. Keep raw evidence and archives private; network exports can include credentials. If source bytes change unexpectedly, the wrong book is edited, another user's private data appears or completed work disappears, stop that operation and preserve the evidence/backup before trying recovery. Continue unrelated safe work where possible.

## What a successful real-life trial looks like

- The incoming collection is accessible through your account and indexed without unexplained loss or duplication.
- You can process useful groups, pause for the day and continue without losing corrections or review decisions.
- Mixed path patterns, provider matches and batch organization reduce real effort while leaving uncertain decisions under your control.
- Corrected books are easier to find, organize and read; lists and notes remain useful afterwards.
- Background jobs, failures and stale-data conflicts explain their state and offer a workable next step.
- Source files stay unchanged except for individually intended, reviewed source operations.
- You keep the resulting catalogue and curation. No test-account migration or throwaway restart is required.

This is evidence from real use, not a replacement for isolated technical recovery/security tests or final release certification. The purpose of this handbook is to help you get through the actual incoming work and uncover problems along the way.
