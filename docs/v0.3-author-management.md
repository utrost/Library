# Author management for release 0.3

Status: implementation started on `develop/0.3`, 2026-10-13. Release 0.3 is now the first planned App Store submission.

Release 0.3 introduces author identities, consistent author names and a dedicated author editing and merge workflow. Books reference those identities through an ordered relationship. A correction to an author then benefits every linked book, including browsing and duplicate detection.

The signed 0.2.0-beta.3 GitHub release remains the preserved baseline. App Store submission is postponed until 0.3 author management and release verification are complete.

## Current storage and intended outcome

Currently, each publication in `library_items` stores an ordered array of names in `authors_json` and a compatibility string in `creators`. The EPUB importer reads individual creator entries, but does not retain separate author sort names. There is no dedicated author identity table.

Example outcome:

- John Doe has a preferred display name of “John Doe” and a sort name of “Doe, John”.
- Books credited to “John Doe” and “Doe, John” can link to that same author.
- “J. Doe” is a possible match requiring review, since it might mean Jane Doe.
- The original credit remains available per book even after the preferred name changes.
- Different people with the same name can have separate records.

Relational normalisation establishes shared identities. Name comparison helps find candidates; it does not prove that two credits identify the same person.

## Scope

Include author records, import normalisation, ordered book relationships, author browsing and editing, reviewed merging, conditional undo and reassignment of incorrectly linked books.

Do not add a dedicated aliases table in this release. A merge records a decision about existing author records and their books; it does not establish a permanent rule that every future “J. Doe” means John Doe. New ambiguous credits may require review again.

External identity services, biographies, author photos, automatic file rewriting and a general contributor-role system are later candidates. Preserve existing source metadata so those extensions remain possible.

## Data model

Proposed tables and fields; final migration names and types must follow repository database conventions.

| Table | Principal fields | Purpose |
| --- | --- | --- |
| `library_authors` | id, user_id, display_name, sort_name, given_name, family_name, comparison_key, revision, field provenance | One author identity within a user's library |
| `library_item_authors` | id, user_id, item_id, author_id, position, source_name, source_sort_name, assignment_source, revision | Ordered authors of an existing publication |
| `library_author_operations` | id, user_id, operation, status, before/after references, expected revisions, timestamps | Durable merge progress and conditional undo |

Use existing `library_items` as the books table. Given and family names are optional; display and sort names support organisations, pen names, initials and names that cannot safely be split.

Relationships preserve original source credits and distinguish imported assignments from explicit user choices. Detailed observations remain in the existing metadata provenance mechanism; do not duplicate complete metadata snapshots on every relationship.

Index author lookup by user and comparison key, directory ordering by user, sort name and id, and relationships by user/item/position and user/author/item. Comparison keys are non-unique: homonyms must remain representable. Enforce unique positions within each book. If merging creates repeated credits for the same identity, retain the earliest position and preserve the original credits in provenance and undo data.

All lookups and mutations enforce user ownership on both ends of the relationship. Account deletion removes authors, relationships and operation history. Removing a book removes its relationships; empty authors remain visible through an “Unused authors” filter and can be deleted explicitly.

## Import and name normalisation

Keep the original credit separate from comparison values. Normalise whitespace and Unicode for matching, using a versioned algorithm. Case folding belongs in the comparison key, not in the displayed name. Do not discard accents, reorder arbitrary words or expand initials automatically.

| Input or evidence | Proposed handling |
| --- | --- |
| A separate embedded creator entry | One author credit |
| John Doe | Preserve display name; default sort name to the supplied name if no reliable sorting data exists |
| Doe, John with an explicit inverted-name convention | Compare as John Doe; retain the original credit and use Doe, John for sorting |
| J. Doe | Preserve initials; offer full-name candidates for review |
| A comma in arbitrary legacy text | Do not split into people or assume surname/given-name structure |
| Semicolon or other configured author separator | Split only according to the explicit importer or inference rule |
| Supplied creator sorting metadata | Retain as a sort-name candidate, associated with the correct creator |
| Conflicting sort names for an existing author | Preserve a user edit; present the new value for review |

Implementation should support OPF creator sorting attributes and EPUB3 creator refinements, with fixtures verifying creator association and precedence. A book-wide Calibre author sorting string must not be blindly assigned to every author of a multi-author book.

For a new credit, reuse a single unambiguous existing record on a conservative full-name comparison. This is a practical initial assignment, not a guarantee of identity; reassignment must always be possible. If multiple records match, or matching requires initials, fuzzy spelling or an unconfirmed comma convention, create an unresolved separate author and offer candidates. Never automatically merge existing identities.

Do not let incomplete metadata from one new book overwrite the preferred name of an established author.

## Rescans and manual corrections

Unchanged source credits retain their existing relationship identities. A manual merge, reassignment or author-name edit must survive ordinary and full rescans.

If a source credit changes:

1. Update its source observation and compare it with the previous observation.
2. Refresh an automatically assigned relationship only when the mapping is unambiguous.
3. Preserve a manually assigned relationship and flag a conflict for review.
4. Treat creator additions, removals and ordering changes as changes to the author field; never silently discard a protected user decision.

Use existing field protection and provenance consistently for scanner imports, filename inference, manual book editing and metadata Apply/Undo. Book editing offers an author picker with “Create author” and “Assign a different author”. Clearly distinguish changing one book's credits from editing the shared author record.

## Author screens

### Directory

Add “Authors” to the left navigation. Provide a paged directory with search, preferred name, sort name and book count. Filters include all authors, possible matches and unused authors. Search may include indexed original book credits without treating them as identity aliases.

Select a row to open its author page. Selecting two or more rows exposes “Merge authors”; users can initiate a merge even if the matcher did not suggest it.

### Author page

Show the preferred name, book count and paged books first. Offer “Edit author” and “Merge with another author” as direct actions.

Editing includes display name, sort name and optional given/family names. Show that saving affects the displayed author on all linked books. Original credits remain available in book details. Support selecting books and assigning them to an existing or new author to correct accidental grouping.

Help text belongs on label tooltips, available on keyboard focus and touch as well as hover. Keep errors, progress, conflict notices and the consequences of a merge visibly readable.

### Merge review

Show the selected authors, their name fields, representative books, original credits and affected-book counts. The user chooses the surviving author and preferred field values, then confirms one merge.

The merge preview must make clear that book files are untouched. Repeated author links on the same book are combined while preserving order and original credit evidence.

After completion, show the result and an Undo action; operation history keeps Undo discoverable later. Stale previews must be refreshed before applying.

### Recovery

Retain retired author records and the exact relationship changes required to reverse a merge. Undo restores only data still matching the operation's expected post-merge state. Later book imports and unrelated edits must remain intact.

If affected records changed afterwards, explain the conflicts and offer review/reassignment rather than blindly restoring an old snapshot. Define and display the undo retention period before shipping; expiry must never delete active author assignments.

## Integration with the catalogue

Author pages and filters query author IDs. Duplicate detection compares confirmed/resolved author identities while retaining title, issue, series and ISBN/content evidence; sharing an author is never sufficient to call two books duplicates.

Keep `authors_json` and `creators` temporarily as compatibility projections, with a single documented write path. After migration, relationships and author records are authoritative. Rendering and author search should use canonical names; any projection refresh must be resumable and tracked so stale strings cannot silently drive different results.

Invalidate affected author facets, search data and duplicate suggestions after edits or merges. Update saved author filters to identity references where mapping is unambiguous; preserve ambiguous legacy filters with an explicit review state rather than silently broadening them.

Export/import must retain author order, source credits and preferred names. Database-local author IDs alone are not portable identities. Existing book lists, reading state and file references must remain unchanged.

## Migration and performance

### Upgrade contract after 0.2

There are currently no known external users. Once distributed through the App Store, releases must support upgrades of existing libraries without requiring a reset or reimport. Treat the already published 0.2 prerelease schema as a stable baseline too: preserve shipped migrations and add new versioned migrations for subsequent schema changes.

The existing `lib/Migration/Version*.php` framework handles schema changes. For author management, distinguish two jobs:

- **Schema migration:** add author tables, relationships and indexes through a new migration. Maintain `appinfo/database.xml` and the schema documentation as reference snapshots; editing those files alone does not upgrade an installed database.
- **Data migration:** populate the new relationships from existing book metadata using a resumable background backfill. Preserve author order, source credits and manual corrections, along with books, lists, notes, reading state and saved filters.

Fresh installation and upgrade from a populated 0.2 library are both release requirements. Keep legacy fields readable during the transition; do not remove them before the backfill and dependent readers have been validated. Expose progress and retryable failures so administrators can distinguish an ongoing migration from completion.

The 0.3 release gate includes a populated 0.2 → 0.3 upgrade, a fresh installation, interruption and retry, concurrent imports and user edits, and migration performance on a large library. These checks must demonstrate preservation of existing data, not merely successful table creation.

### Backfill and runtime performance

Use an additive schema migration followed by a bounded, resumable backfill. Do not perform a full library rewrite inside a single upgrade request.

Read ordered `authors_json` first. For legacy `creators`, use existing conservative parsing; never split arbitrary comma-separated text. Reuse unambiguous exact normalised full names within one user's catalogue, with a supported way to separate homonyms. Keep ambiguous variants separate for later review.

Track migration progress and make batches idempotent. Concurrent imports and edits need a consistent transition strategy: dual-write through one service, revision checks and an atomic per-user switch to authoritative relationships. Keep existing browsing available while backfill runs; enable merge operations only after that user's backfill is complete.

Use batched author reads for catalogue pages, indexed lookups during import and indexed candidate retrieval rather than all-pairs fuzzy comparisons. Paginate author books and match lists. Candidate limits should be visible when a result is incomplete.

Small merges can use one transaction. Large merges need a persisted operation with bounded batches, affected-record concurrency checks and an atomic visible completion strategy. Do not expose a partially reassigned identity as a completed merge; cancellation and retry must have defined recovery behaviour.

Measure the existing developer library before and after implementation: import throughput, SQL count and time, catalogue and author-page latency, directory search, merge throughput, duplicate lookup latency and migration database growth. Record actual available books and relationships separately from missing catalogue rows. Agree regression budgets from that baseline; do not claim performance targets as measured results.

## Delivery slices

1. **Storage and migration:** author service, ownership constraints, relationship backfill, source credits and rescan protection.
2. **Read integration:** author directory/pages, author-ID filters, import reuse, catalogue and duplicate integration.
3. **Editing and recovery:** shared-name editing, book reassignment, merge preview, durable execution and conditional undo.
4. **Release hardening:** portability, saved filters, cleanup, accessibility, performance evidence and exact-package compatibility checks.

Each slice should be reviewable on the developer NC34 instance. Complete the cross-version release matrix after the integrated workflow is accepted. The frozen 0.2 signed candidate remains unchanged; the first App Store release will be 0.3.

## Acceptance criteria

- Multiple books link to one author and multiple authors retain their order on a book.
- John Doe / Doe, John follow the configured convention; J. Doe remains ambiguous.
- Same-name people can be separated; organisations, mononyms, accented names and compound surnames remain intact.
- A shared-name edit is reflected consistently in browsing, filtering and duplicate suggestions.
- Merge and undo preserve source credits, files, book lists, reading state and unrelated edits.
- Manual identity assignments survive rescans, inference Apply/Undo and changed embedded metadata.
- Migration resumes safely after interruption and handles concurrent imports without duplicate relationships.
- Two users cannot see or modify one another's author identities or operation history.
- Large-library measurements include repeatable SQL and browser evidence, with bounded candidate work.
- Playwright covers import, directory search, editing, merge, conflicting undo and reassignment on developer NC34; release checks cover supported NC33–35 and fresh/upgrade paths, subject to the release's final compatibility declaration.

## Decisions to settle during implementation

Choose an undo retention period and the threshold for background merges from measured operation sizes. Confirm the directory and merge preview with real examples before expanding the UI. The agreed scope remains: normalised author identities and practical editing/merging, with no dedicated aliases system.

## Storage slice — 0.3.0-alpha.1

Implemented and deployed on developer NC34. Fresh/populated-upgrade checks, migration assertions and Chromium/Firefox author workflows passed. See the [0.3-alpha.1 verification](compatibility-evidence/2026-10-13-author-management-alpha1/README.md) for measurements and remaining release gates:

- Additive `Version000300Date20261013120000` creates author identities, ordered book relationships and a per-user coordination row. No files or legacy metadata are rewritten by this migration.
- `AuthorIdentity` version 1 normalises NFC, whitespace and case for comparison. It preserves accents, commas and initials. Inverted-name conversion is available only through an explicit argument; migration does not assume that convention. Unicode normalisation support is required so keys cannot vary silently between installations.
- `AuthorStorageService` builds shadow relationships from ordered `authors_json`, with conservative unsplit legacy `creators` fallback. Invalid stored author data is reported as a failure rather than silently migrated as an empty credit list.
- A pending flag is written in the same SQL update as author changes, including manual edits, candidate acceptance, imports and inference Apply/Undo. Unchanged scanner credits do not requeue completed books.
- Each book is read and reconciled under a transaction and item lock, followed by a per-user identity lock. Unchanged credits retain identities. Multiple exact-name candidates remain separate; there is no automatic fuzzy merge.
- Changed credits on a manually assigned relationship stop at a conflict. Future merge/reassignment code must mark protected assignments and follow the same lock order.
- Book/root removal deletes relationships. Account deletion removes all author storage. Unused identities remain available for future directory cleanup.

`AuthorBackfillJob` processes chunks of at most 500 books within a five-second budget between items per invocation, subject to the server's cron frequency. The time budget does not interrupt a running SQL statement or transaction. Failures are recorded per book and logged; they do not block later books. The developer run completed all 107,717 catalogue records; the measured CLI phase took 391 seconds at approximately 275 records/second. This includes missing catalogue entries and is not an ebook import benchmark.

Operator commands (after installation of this development version):

```sh
# Read-only counts: synced, pending, conflict, failed; authoritative stays false.
php occ library:authors:migrate USER_ID
# One bounded batch, at most 500 books / five seconds between items.
php occ library:authors:migrate USER_ID --run
# Requeue failures, then attempt one batch. Manual conflicts stay protected.
php occ library:authors:migrate USER_ID --retry-failed --run
```

The existing author arrays remain authoritative for catalogue browsing and duplicate detection in this slice. An empty pending count does not enable merging or switch readers. Author directory, paged books, prefix search, unused-author filtering and preferred/sort/given/family-name editing are now available. Editing is blocked while initial migration work or failures remain. Stale saves are rejected and drafts retained. Next work: embedded creator sort metadata, reviewed merge/reassignment and the explicit authoritative switch for catalogue filters and duplicate detection. The operations/undo table will be introduced with that workflow rather than as unused storage.
