# v0.2 proposal: metadata from paths, portable metadata and filing

Status: staged scope, updated 2026-09-26. Saved guided/advanced definitions, folder assignments and combined sample previews are implemented in alpha.14. Review/apply, metadata writing and filing are not implemented. The beta's existing filename inference, catalogue editing, exports and scan jobs provide the starting point.

## Intended workflow

Choose books or a root → infer metadata → review suggested fields → apply selected changes → optionally write sidecars or preview filing → run approved operations → refresh affected catalogue items.

Metadata improvement is useful on its own. Sidecar writing and physical filing are separate choices; accepting a title suggestion must not also move a book or create files.

## 1. Infer useful metadata from filenames and paths

The [detailed inference feature design](v0.2-inference.md) defines the guided UX, complete placeholder vocabulary, saved/versioned templates, folder rules, review/apply behavior, dependencies and delivery slices.

The existing `lib/Metadata/FilenameMetadataExtractor.php` recognizes title/creator, dated-magazine, year/issue, numbered-comic and some folder patterns. Extend this with named rules assigned to selected folders within a configured Library root and a preview on sample files. Parse paths relative to the assigned folder, excluding account names and unrelated parent directories.

Example, with a user-selected `{subject}/{creator}/{title}` folder convention:

```text
Mathematics/Emmy Noether/Collected Papers.pdf
→ subject: Mathematics
→ creator: Emmy Noether
→ title: Collected Papers
```

Offer explicit conventions for both `Author - Title` and `Title - Author`. A separator alone cannot establish which is correct. Show the matching rule, original path, proposed value and reason for each field. Ambiguous values remain suggestions; do not assign invented confidence percentages.

Folder mappings can suggest subjects such as Mathematics or Fiction. A subject or genre must remain distinct from publication form (book, magazine, comic) and file format (EPUB, PDF). A generic title cannot establish its subject without further evidence.

Keep manual values protected. Filename/path suggestions fill gaps by default; replacing existing embedded or sidecar values requires selecting those changes in the preview. Preserve field provenance and record the ruleset version so changed rules can trigger targeted reprocessing. Applying accepted metadata updates the catalogue immediately.

## 2. Write portable metadata

Recommend OPF sidecars as the first interoperability target. Library already reads matching OPF sidecars, and calibre exposes OPF metadata import/export. Compatibility still needs an explicit field mapping and round-trip checks against intended consumers; an OPF file is not a universal store for every Library field.

| Destination | Proposed role | Sequence |
| --- | --- | --- |
| Library database | Current catalogue and accepted corrections | Existing baseline |
| `Book.opf` beside `Book.epub` or `Book.pdf` | Portable bibliographic fields | First write-back slice |
| Library JSON export/sidecar | Richer Library-specific portability | Existing download export; direct writing considered separately |
| Embedded EPUB, PDF or CBZ metadata | Metadata travels inside the publication | Later, format-specific writers |

For the first sidecar slice:

- Start with a downloadable OPF preview, then allow an explicit write beside selected books through Nextcloud's filesystem API.
- Show fields and destination before writing. Exclude personal stars, ratings, reading activity and private workflow state by default, especially for shared folders.
- Prefer one matching sidecar per publication. Do not create folder-wide `metadata.opf` in a folder containing unrelated books.
- Treat identical basenames with different formats as an ambiguity until the user explicitly groups them as the same publication; never assume two editions share metadata.
- Create new sidecars first. Existing OPFs require a comparison and an explicit supported merge/update policy. Preserve unknown fields or decline an update that would discard them.
- Keep recoverable prior content before replacing a sidecar. Recheck source/target identity, permissions and modification state at execution time; changed files become conflicts for review.
- Track the generated sidecar and the accepted metadata revision, so reading our own output back does not manufacture new suggestions or repeated writes.

Embedded writing follows separately: EPUB package metadata, PDF metadata and CBZ ComicInfo each need a dedicated writer, format validation and a recovery plan. Support and preservation of unknown metadata must be proven per format before offering replacement of original files.

## 3. File books using accepted metadata

First offer a preview of proposed physical moves using ordered rules and destination templates, for example:

```text
subject contains Mathematics → /Books/Mathematics/{creator}/{title}.{extension}
subject contains Fiction     → /Books/Fiction/{creator}/{title}.{extension}
```

Collections and subject filters can group a book in several places already. Physical filing chooses one destination, so multiple matching rules need explicit priority or a review decision. Missing metadata leaves the item unfiled with an explanation.

The preview must list current and proposed paths, companion sidecars, collisions and permission failures. Sanitize generated path segments and constrain destinations to selected writable Library roots. Never overwrite an existing publication to resolve a collision.

Start with approved moves within one storage and configured roots. Cross-storage moves, shared-library ownership changes and moves outside indexed roots need separate design because identity and access can change. Resolve the actual file after a move and preserve the catalogue relationship where supported; do not assume file IDs survive every storage operation.

Move paired sidecars with the publication and keep an operation journal. A multi-file move can fail after the first file succeeds; report partial completion and offer a recovery action rather than claiming the whole operation was atomic. Undo must recheck intervening changes and collisions.

Filing uses accepted metadata. Do not feed a generated destination back into classification as new independent evidence: otherwise a move can alter its own classification and trigger another move.

## 4. Queue work and refresh affected items

Reuse Nextcloud background jobs and the existing scan progress/cancellation UI. The current scanner queues all-root, single-root, metadata-error and missing-file work; it needs an affected-file scope and persistent per-operation progress for these workflows.

- Persist the approved plan, user, file identities, metadata revision and expected modification state. Recheck access when each item executes.
- Process bounded batches with per-item outcomes, retry limits and checkpoints. Repeated delivery must not repeat a completed move or write.
- Coordinate operations on the same book so a scan, sidecar write and filing job cannot apply conflicting changes concurrently.
- Cancellation stops pending work; it does not silently roll back completed operations. Show which actions finished and which require recovery.
- After a sidecar write or move, enqueue a targeted Library refresh for affected primary files and their sidecar relationships. Coalesce events and recognize our own operations to prevent loops.
- Metadata-only catalogue edits need no filesystem rescan. Full root scans remain a reconciliation fallback; do not schedule a full-instance Nextcloud scan after each book operation.
- Surface jobs waiting for Nextcloud's background worker so users can distinguish waiting from failed work.

All file access and mutations must use Nextcloud's public filesystem APIs. Confirm API availability on 33, 34 and 35 before implementation; the moving `latest` documentation currently includes upcoming-version additions.

## Product boundary and delivery order

The beta delegates source-file organization and source-folder writes to external tools. This proposal deliberately extends Library with user-approved sidecar writing and filing. The beta's behavior and release promise remain the baseline until each new operation is implemented and verified.

1. **0.2 first slice:** rules scoped to roots, metadata inference preview, selected-field apply, and real filename/path examples covering ambiguity and manual-value preservation.
2. **Portable metadata:** OPF download and read-back, then queued creation of new OPF sidecars. Add existing-sidecar update only with loss-preserving behavior.
3. **Filing:** destination rules and dry-run preview, followed by approved moves with journal and targeted refresh.
4. **Later:** embedded metadata writers and broader automated filing after the explicit workflows are reliable.

The first slice is a useful release independently. Whether sidecar writing and filing ship in the same 0.2 release depends on the recovery and interoperability evidence, rather than making every feature a prerequisite.

## Acceptance evidence to build with implementation

- Real sparse-metadata EPUB/PDF/CBZ examples and conflicting filename conventions yield explainable suggestions; accepted edits survive rescans.
- OPF output reads back into Library and an intended external consumer without losing supported fields; unsupported fields and basename collisions are explicit.
- Read-only folders, quota failures, concurrent edits and revoked permissions leave clear per-item outcomes.
- Worker interruption and retries do not duplicate actions; partial book/sidecar moves can be recovered.
- Filing preserves publication content, related sidecars and catalogue identity within the supported move scope; collisions never overwrite another book.
- Repeated targeted refreshes settle without write/scan/move loops on Nextcloud 33–35.
