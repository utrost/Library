# Library v0.1 Technical Specification Draft

Status: draft

## 1. Product boundary

Library is a Nextcloud publication catalogue. It indexes and enriches existing files but does not own, import or render them.

Library owns discovery, metadata, cover references, browsing, search, manual edits and reader handoff.

Reader/viewer apps own EPUB/PDF/comic rendering, page navigation, annotations, bookmarks and reading position.

## 2. Supported environment

Initial development target:

- Nextcloud 34
- conventional Nextcloud PHP app backend
- Nextcloud AppFramework controllers/routes/templates
- MariaDB-backed Nextcloud database through Nextcloud database APIs
- Vue/Vite frontend mounted in a conventional Nextcloud `#app-content` shell, with a no-Vue fallback renderer for core browse actions

## 3. Initial data model direction

Use separate root, file-index and catalogue-item concepts:

- `library_roots`: per-user configured scan roots; the UI may start with one root, but the schema and services must support multiple roots from the beginning
- `library_files`: operational file index keyed by stable Nextcloud file id and associated with the root that discovered it
- `library_items`: editable publication metadata for one indexed file in v0.1
- scanner field-source and scanner-candidate JSON maps on catalogue items for the current field-level provenance/reset workflow
- `library_metadata_candidates`: optional future normalized extracted/inferred source-candidate table
- `library_covers`: optional future generated/extracted cover cache references

v0.1 can keep one file = one item, but should not make that irreversible.

## 3.1 Metadata storage policy

Library separates source-file facts from publication metadata and Nextcloud-wide collaboration metadata.

- `library_files` stores technical Nextcloud file identity and scan state.
- `library_items` stores canonical Library publication metadata for v0.1.
- Nextcloud system tags are exposed as file-level cross-archive classification such as interests, projects, collections and statuses.
- Nextcloud comments are exposed/addable as file-level discussion/notes, not structured catalogue fields.
- Nextcloud FilesMetadata may later mirror a compact searchable summary, but it is not the primary normalized catalogue database.
- Corrected metadata can be exported as side-effect-free JSON, previewed for restore matching, applied to matched existing Library items, mapped to proposed `.library.json` sidecar paths, and downloaded as a sidecar ZIP without writing source-folder files.

Format-specific extractors must map EPUB/PDF/CBZ metadata into this general model. File format is technical metadata; publication form/type is semantic metadata.

Initial `library_roots` shape:

```text
id
user_id
path
label
enabled
last_scan_at
created_at
updated_at
```

Root rules:

- roots are user-specific in v0.1;
- a user may eventually configure many roots such as Books, Comics, Magazines and Manuals;
- the first UI may expose only add/edit/remove for one path, but the backend must not assume a singleton;
- scanners should iterate all enabled roots for the current user;
- duplicate files discovered through overlapping roots should be deduplicated by file ID, with the first/root-specific discovery retained for diagnostics.

## 4. File identity

Prefer Nextcloud file IDs over paths. Cache paths only for display and diagnostics.

Move/rename behaviour:

- same file id: update cached path;
- missing file: mark missing/unavailable first, do not immediately delete user metadata;
- changed etag/mtime: rescan derived metadata while preserving user overrides.

## 5. Scanner lifecycle

Manual scan first:

```text
current user
  -> enabled configured roots
  -> recursive walk per root
  -> supported format check
  -> file id lookup
  -> upsert library_files by file id
  -> remember discovering root for diagnostics/filtering
  -> extract/infer metadata
  -> upsert library_items while respecting user overrides
```

Important current scan states:

- indexed
- metadata_error
- missing
- sidecar

Scan requests are queued as Nextcloud background jobs. Library records app-owned job state (`queued`, `running`, `completed`, `failed`) with all-roots or per-root scope, progress counts, duration and summaries.

## 6. Format adapters

Initial preference:

- EPUB/OPF: package metadata through the OPF/EPUB extractor; same-basename and folder-level OPF sidecars can override primary file candidates
- PDF: file identity and basic document metadata through the PDF Info extractor; cover via Nextcloud preview where possible
- CBZ: ZIP contents, first image covers, and ComicInfo.xml metadata through the CBZ extractor
- Filename/folder patterns: low-precedence magazine, dated issue and numbered-comic candidates
- CBR: optional/deferred unless a clean dependency path exists

PDF format must not imply publication type `Book`.

## 7. Reader integration

Reader integration is the first spike. Desired abstraction:

```php
interface ReaderProvider {
    public function canOpen(File $file): bool;
    public function getOpenUrl(File $file): ?string;
    public function getLabel(): string;
}
```

v0.1 fallback ladder:

1. known compatible reader/viewer provider;
2. Nextcloud Viewer / default file route;
3. Show in Files;
4. download/open externally.

## 8. Frontend views

Current v0.1 views:

- compact cover-first catalogue grid with database-backed search/filter/sort/pagination
- item detail workbench with metadata edit, scanner-candidate provenance, reset-to-scanner actions, tags, comments and file diagnostics
- personal Library settings for roots, queued scans, per-root scan actions, scan progress/history and indexed-file diagnostics
- corrected-metadata JSON export, no-write metadata import preview, matched-item import apply, sidecar manifest export and sidecar ZIP export
- portability surface summary: corrected-metadata JSON export, import preview, matched-item apply, sidecar manifest and sidecar ZIP

Future views:

- dedicated creator/series/publication/year landing pages
- saved views/smart collections
- richer scan repair and metadata review queues

## 9. Permissions and multi-user behaviour

Start per-user. Each user configures their own roots and metadata. Search results must only expose files accessible to the current user.

Shared/global library scopes are deferred.

## 10. Testing strategy

- Python/static contract tests for repository skeleton during bootstrap
- PHP syntax checks inside the Nextcloud container
- `occ app:enable library` integration smoke
- Nextcloud route smoke via `/apps/library/`
- Python/static contract tests for services/controllers/templates/docs
- Vue/Vitest smoke for frontend components
- browser/CDP smoke for real Vue mounting, CSS assets, compact cards and detail accessibility

## 11. Packaging and App Store later

Deferred until the current development catalogue is release-hardened. Track AGPL licensing, app signing, screenshots, translations, packaging, first-run onboarding, scan repair controls and known limitations before public App Store submission.
