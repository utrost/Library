## Composite folder examples (alpha.7)

- `english_science_fiction`: split `_` at the **first occurrence**; assign Language to `english` (normalized to `en`) and Genre to `science_fiction`; enable underscore replacement. Optionally map `science fiction` to `Science fiction`.
- `Sanderson - mistborn series`: split ` - ` at the first occurrence; assign Author and Series; remove the literal suffix ` series` from the series. No first name is invented.
- `Gaiman, Neil; Pratchett, Terry`: assign Author, select the semicolon author separator, optionally enable surname/given-name conversion. Result: two chips, `Neil Gaiman` and `Terry Pratchett`.
- To extract several authors from different segments, assign each Author and enable **Combine authors from multiple parts**. Without that option, differing captures are ambiguous.

Transform order: trim input, remove required literal prefix/suffix, replace underscores if selected, trim, apply an exact value mapping, normalize language, then split/format authors. Missing required affixes and structural mismatches yield unmatched; empty or invalid transformed values yield invalid. Nested splitting is bounded to six levels and 128 visited nodes per path. No metadata or files are written.

## Unified pattern selector (alpha.11)

One alphabetical **Pattern** selector includes supplied and personal definitions. Selecting an option immediately updates the active pattern and preview. Manual edits display **Custom pattern** when they no longer match a stored definition. The advanced text appears once; examples and explanatory guidance live in accessible label tooltips. Save-as-new and confirmed deletion sit alongside the name field. Deleting a supplied pattern hides it only for the current user; deleting a personal pattern removes its stored definition. Neither operation changes the current preview or any publications.

Tooltips open on label hover, help-button keyboard focus or tap, and close with Escape, outside interaction or scrolling. Errors and unmatched states remain visible. The same compact-help policy applies to future app screens (see `ux-concept.md`). Production build and deployment only; browser tests not rerun for alpha.11.

## Built-in and saved advanced patterns (alpha.10)

Advanced-pattern mode includes ten presets, each displaying its literal pattern and an example path before loading. They cover filename-only titles, `Title by Author`, `Title - Author (Year)`, `Author - Title`, author folders, numbered series folders, inline `Series #Number`, language/subject folders and underscore-separated series filenames. Paths are relative to the selected scope; the language/subject presets contain a literal `books/` prefix that may need editing. A preset does not infer missing titles, strip promotional wording or resolve ambiguous delimiters.

**Save current pattern as new** stores a private named pattern in Nextcloud user preferences (up to 100, name up to 120 characters, pattern up to 1000). Names must be distinct; loading an existing pattern and editing it does not silently overwrite the saved copy. **Pattern** provides immediate loading and confirmed deletion in one list. Supplied patterns can be saved as customized copies or hidden from the user’s list. Deletion only removes the saved definition, leaving the current preview and publications untouched.

The API derives ownership from the authenticated session and keeps CSRF protection on writes. Separate preference keys avoid one tab overwriting an unrelated pattern saved in another tab. Alpha.13 also persists guided assignments, nested splits, transformations and author options. Folder scope, selected records and automatic execution are excluded. Selecting a saved rule restores it immediately; deletion requires confirmation and keeps the active preview. Alpha.16 provides a separate, explicitly approved metadata Apply endpoint.

## Series position (alpha.9)

Assign **Part in series** to a folder or filename piece, or use `%seriesNumber%` in advanced patterns. For `Orchard Notes/2.5_Autumn Appendix_Ada Quill.epub`, use:

```text
%series%/%seriesNumber%_%title%_%author%.%extension%
```

The preview shows Series `Orchard Notes`, Part in series `2.5`, Title `Autumn Appendix`, and Author `Ada Quill`. Position labels are preserved as text; leading zeros, decimals and Roman numerals are not coerced to integers. Alpha.15 provides dedicated text storage and export/import mapping; alpha.16 permits approved Apply for this field. Numerical series sorting is still pending.

Alpha.9 validation is limited to the production build; browser suites were not rerun.

## Outcome and scope

A user can teach Library how their folders and filenames encode publication metadata, review the interpretation across a mixed collection, apply selected values, and save the rules for reuse. One root may contain several conventions and arbitrary folder depths.

Inference can ship independently. It changes catalogue metadata only; OPF/JSON sidecar writing, embedded metadata updates and physical filing are subsequent explicit workflows. No external metadata provider or AI service is required.

## Guided workflow

1. **Choose files or a folder.** Show the scope, file count, and an explicit include-subfolders option. Offer a varied sample covering different subfolders, depths, extensions and naming patterns. The sample is a teaching aid; full-scope analysis is required before reporting total match counts.
2. **Teach by example.** Click folder segments or highlight filename text and label it Title, Author, Genre, Ignore, etc. Provide equivalent keyboard-accessible segment/text controls. Common fields appear first, with less common fields under More fields. Generate the template internally; an advanced editor can display/edit it with syntax help and clear validation errors.
3. **Preview while editing.** Display original paths, current values and proposed values. Explain the matching rule and source segment. Show matched, ambiguous, invalid and unmatched outcomes instead of unexplained confidence scores. Do not apply edits during preview.
4. **Handle another convention.** From unmatched examples, offer Create another rule for these files. Users can narrow the folder or filename scope without building a single template with many optional branches.
5. **Review the full scope.** Present counts and paginated results with filters for conflicts/unmatched files. Allow selection of items and individual fields. Default to filling empty fields; replacement of existing values is explicit. Never treat all matching results as selected merely because one page is visible.
6. **Apply and keep the result.** Show a precise summary of selected changes, then progress and per-item outcomes. Save the rule and optional folder assignment. Preserve drafts and review selections across navigation/reload. Offer undo for the batch where no later change conflicts with restoration.

Prototype this flow against deliberately mixed example paths before implementing the complete parser. The usability goal is that a person can extract correct titles and authors without learning `%title%` syntax. Cover mobile, keyboard and assistive-technology use in the prototype review.

## Templates and folder rules

**Template:** a named, reusable naming convention containing capture fields, literal separators, validation and optional normalization. It has a version, an example set and no personal folder assignment.

**Folder rule:** a template version assigned to a selected folder inside a Library root. It adds recursive scope, optional extension/name constraints, fixed metadata values and an application policy. Paths are interpreted relative to this selected folder, never relative to an account directory or arbitrary parent of the configured root.

For example, a Mathematics folder rule can set `subject = Mathematics` and `language = de`, while its template extracts author and title from names. Fixed values and extracted values must not silently disagree: show the conflict during rule editing or result review.

Users can name, save, duplicate, edit, disable, preview and delete their own templates and rules. Disabling/deleting a rule stops future use and does not erase previously accepted metadata. Rules are personal in the first release; an administrator/shared rule library is a later feature.

Template edits create a new version. Folder rules pin their applied version until the user previews and adopts an update. Saved example files show before/after results when editing. Changed, inaccessible or deleted example files are marked as such; never silently replace them with different files. In-flight previews and jobs retain their original version and scope.

Template import/export is part of the intended feature, but may follow the first local rule-management slice. Export syntax, mappings and schema version without folder assignments, user IDs, file IDs, or private example paths. Include examples only by explicit choice. Validate imported templates; importing never activates a folder rule.

## Matching and precedence

- Match the whole relative path, including its filename. Literal text/separators are meaningful. A capture normally stays within one path segment.
- A matching rule assigned to a deeper folder wins over matching ancestor-folder rules. If the deeper rule does not match, an ancestor rule can still be considered; show which rule was used.
- If several equally specific rules match, agreement on a field is usable and differing values require review. Do not silently use whichever rule happens to execute first. Unmatched files remain unchanged.
- Multiple templates are preferable to optional-template syntax in the first release. Repeated captures must agree, except fields explicitly configured as lists.
- Wildcards and captures have bounded execution and validated lengths. The initial editor does not execute arbitrary code or user-provided regular expressions.
- Preserve original text alongside normalized candidates. Normalization such as underscore-to-space, language mappings or author-name order must be visible and configurable. Never split authors solely on spaces or commas.

Example advanced template:

```text
%genre%/%language%/%series%/%title%_%seriesNumber%_%author% [%ignore%].%extension%
```

The brackets delimit an ignored suffix. A bare `%author% %ignore%` cannot reliably split a multiword author from arbitrary trailing words; show an ambiguity and ask for a known delimiter/suffix or another template. Dates, dots in names and decimal series numbers must survive normalization.

## Supported placeholders

These are the intended 0.2 vocabulary, not a claim that every field already exists in the beta schema.

| Placeholder | Meaning and handling |
| --- | --- |
| `%title%` | Publication title |
| `%subtitle%` | Subtitle |
| `%author%` | Creator name or names, using an explicitly selected list separator |
| `%series%` | Series name; preserve its meaning distinctly from periodical publication names |
| `%seriesNumber%` | Position in a series; preserve labels and values such as `2.5` |
| `%genre%` | Genre, distinct from subject, publication form and file format |
| `%subject%` | Topic; allow multiple values with an explicit separator |
| `%language%` | Validated language code or a user-visible mapping such as English → en |
| `%publisher%` | Publisher |
| `%year%` | Publication year; preserve year-only precision |
| `%date%` | Publication date using a selected format; validate real calendar dates |
| `%edition%` | Edition statement |
| `%volume%` | Volume number or label |
| `%issue%` | Periodical issue number or label |
| `%isbn%` | ISBN candidate with format/checksum validation |
| `%issn%` | ISSN candidate with format/checksum validation |
| `%ignore%` | Consume delimited text within a segment without creating metadata |
| `%folder%` | Consume exactly one complete folder level without extracting metadata |
| `%folders%` | Consume zero or more complete folder levels; multiple valid interpretations remain ambiguous |
| `%extension%` | Match/filter the final filename extension; never infer or change actual file content type |

Reject invalid identifiers/dates for automatic application while keeping their raw text visible for review. Conflicting year/date captures are a review issue. Nextcloud system tags are separate from these placeholders and are not assigned implicitly.

## Accepted values, provenance and reuse

Each field suggestion records the file identity, observed path and modification state, rule/template version, matched segment, raw value, normalization steps and proposed value. An accepted value retains that origin plus the user's acceptance; rescans must not silently replace it with another inference.

The default saved-rule policy is **suggest on future scans**. A later opt-in **automatically fill empty fields** mode can apply unambiguous, valid suggestions from a trusted rule; it must not overwrite accepted/manual values, write sidecars or move files. Empty-but-deliberately-cleared fields need a protected state so automation does not keep refilling them.

Recheck access, current path, metadata revision and rule version before applying a preview. If relevant data changed, mark the item stale and regenerate its preview rather than applying an obsolete interpretation. Unchanged input and rule versions must not keep creating duplicate suggestions.

Provide Dismiss suggestion with suppression for the same field/input/rule version. A genuinely changed source or revised rule can generate a new suggestion. This keeps Review useful on repeated scans.

Record before/after values and provenance for each applied batch. Undo only restores fields still matching that batch's result; later edits require review. Define bounded history retention and show the undo availability period. This is catalogue undo, separate from later file-operation recovery.

## Dependencies and integration boundaries

| Dependency | Current starting point | Work needed for inference |
| --- | --- | --- |
| Catalogue fields | Title, subtitle, creators, publication, dates, language, publisher, subjects/classifications and identifiers exist | Series, series position and genre storage/editing/validation/export/import are implemented in alpha.15; edition, volume and issue remain future work |
| Metadata precedence | Scanner candidates, manual edits and provenance exist | Field-level accepted/cleared protection, structured rule provenance, dismissed suggestions and version-aware reprocessing |
| Rule persistence | Private advanced/guided definitions and folder assignment snapshots now exist | Draft/example references, portable export/import and scan-time suggestion policy remain |
| Preview/review | Existing Review and batch preview/apply patterns | Add inference outcomes, saved review state, stale-preview detection and a bounded batch change journal |
| Background work | Root/repair scan jobs with progress and cancellation exist | Add selected-file inference/apply batches with checkpoints, deduplication and rechecked permissions for large scopes |
| Catalogue refresh | Database-backed browsing/search and derived indexes exist | Apply through metadata services so facets/search/health counts update; do not rescan file contents merely to apply accepted metadata |

Detailed queue work is a shared foundation, not something that must wait for step 4. Small interactive examples can be parsed immediately; full-scope analysis and large apply batches need bounded background processing and visible progress.

**No dependency on step 2 (write metadata):** inference writes accepted values to the catalogue. OPF export later consumes those structured values and has its own field mapping and conflict policy.

**No dependency on step 3 (filing):** filing later consumes accepted metadata regardless of whether it originated in inference, embedded metadata or manual editing. Its destination templates are a separate rule type even if they reuse the field vocabulary.

**Shared with step 4 (queue/refresh):** jobs, progress and version checks can be built incrementally for inference and extended for file writes/moves. Source-file locking, multi-file recovery and storage-specific move behavior are not prerequisites for the inference-only release.

Coordinate field names, provenance, revision checks and file identity now. Later filing must not promote its generated destination to independent evidence and cause a classification/move loop.

## Delivery slices and acceptance

The alpha.6 prototype includes a sticky live preview beside the assignment editor (above it on narrow screens). It compares extracted fields with the selected record's current metadata and flags conflicts. Assignment and pattern edits update immediately; changing the example retains the active pattern. Unmatched, ambiguous and invalid examples explicitly show no extracted fields. This remains a read-only preview.

1. **UX prototype and examples:** mixed depths, different conventions, Unicode names, separators inside titles, multiword authors, decimal series positions and unmatched files. Validate that the guided flow is understandable without template syntax.
2. **Rules and field model:** saved/versioned templates and folder rules, supported-field storage and matching/normalization previews. A displayed capture must have a defined canonical destination before Apply is enabled.
3. **Review and apply:** full-scope results, field/item selection, stale-preview checks, bounded jobs, provenance and conditional undo. Accepted values survive rescans and later rule edits; retries do not duplicate changes.
4. **Reuse and portability:** saved rules on later scans, dismissals, template import/export, and optional trusted-rule empty-field application after the suggestion workflow is reliable.

Acceptance must include overlapping rules, files moving after preview, revoked access, worker interruption, deliberately cleared fields, undo after a later edit, and consistent behavior across supported Nextcloud versions. Template exports must not leak private example paths by default.

## Agreed decisions and remaining choices

Agreed with the user:

- Start with the common fields, adding specialist fields incrementally once storage and validation are ready.
- Require review of suggestions initially; introduce trusted-rule automatic empty-field filling later as an explicit opt-in.

- **Example corpus:** collect representative relative paths from several real conventions, with intended metadata for each. Include ambiguous/unmatched examples, not only clean cases. Anonymized paths are sufficient; book contents are unnecessary for the first prototype.
- **Initial field set:** proposed common fields are title, author, series/position, genre/subject, language and year/date. The exact order can follow the prototype examples; the full vocabulary is staged behind complete storage and validation.
- **Sharing:** recommend personal templates with portable import/export first; shared/admin-maintained templates can follow real demand.
- **Undo retention:** choose a bounded retention period during implementation and expose it in the result/history UI. Avoid a permanent restoration promise.

These defaults allow prototyping now. The most useful user input is a small collection of real relative paths plus the desired extracted fields; it will reveal which matching controls belong in the first UI.
